# Git은 파일의 버전을 어떻게 저장할까?

> **대상:** Git을 처음 배우는 사람  
> **목표:** `newFile`이라는 파일 하나를 통해 `git add`, `git commit`, `git commit --amend`가 Git 내부에서 무엇을 바꾸는지 **눈으로 이해한다.**  
> **학습 방식:** 명령어를 따라 하는 실습이 아니라, **명령 실행 전후의 자료구조**를 비교하는 설명 자료

## 0. 가장 중요한 그림: Git은 파일을 어떻게 기억할까?

예를 들어 `newFile`이라는 파일에 다음 내용이 들어 있다고 가정하자.

**newFile**

```text
created
```

Git은 이 파일을 버전으로 기록할 때, 단순히 `newFile_v1`, `newFile_v2` 같은 복사본을 만드는 방식으로 관리하지 않는다.

핵심은 다음 세 종류의 **Git 객체(object)**다.

| 객체 | 기억하는 것 | 이 예제에서 |
|---|---|---|
| **Blob** | 파일의 **내용** | `created`와 줄바꿈 |
| **Tree** | 파일·폴더의 **이름, 구성, 연결된 객체** | `newFile → Blob a123` |
| **Commit** | 한 시점의 파일 구조(Tree), 이전 버전, 작성 정보와 메시지 | `Tree t456`, 메시지 `add file` |

```text
Commit ──가리킴──> Tree ──가리킴──> Blob
 버전 정보             파일 구조             실제 파일 내용
```

아래에서 사용하는 `a123`, `t456`, `c789`는 **이해를 돕기 위한 가상의 짧은 해시**다. 실제 Git 객체 ID는 더 긴 16진수 해시(SHA-1 방식이면 40자리, SHA-256 방식이면 64자리)이며, 동일한 객체를 식별하는 이름으로 사용된다.

## 1. 파일 하나를 만들었다

다음 명령을 실행했다고 가정하자.

```bash
echo "created" >> newFile
```

내 컴퓨터의 현재 파일은 이렇게 보인다.

```text
내 작업 폴더 (Working Directory)
└── newFile
    ┌───────────────┐
    │ created       │
    └───────────────┘
```

여기서 `echo`는 끝에 **줄바꿈 문자**도 추가하므로, 실제 파일의 바이트는 `created\n`이다. 처음 실행했고 기존에 같은 이름의 파일이 없었다고 가정한다. `>>`는 기존 파일이 있으면 내용을 **덧붙이는** 연산자다.

**이 시점에는 Git 버전이 만들어지지 않았다.** 그냥 내 작업 폴더에 파일이 하나 생겼을 뿐이다.

---

## 2. `git add newFile`: 두 군데에 변화가 생긴다

```bash
git add newFile
```

이 명령을 이해할 때는 **Blob**과 **Index(Staging Area)**를 따로 살펴봐야 한다.

### 2-1. Git 객체 저장소에 Blob이 생긴다

Git은 현재 `newFile`의 내용을 읽어서 Blob 객체를 기록한다.

```text
Git 객체 저장소 (보통 .git/objects/)

Blob
┌───────────────────────┐
│ 객체 ID: a123          │
│ 객체 종류: blob       │
│                       │
│ created               │
└───────────────────────┘
```

**Blob에는 파일 이름 `newFile`이 들어 있지 않다.** Blob은 기본적으로 **파일 내용의 바이트**를 나타내는 객체다.

따라서 다른 경로에 있는 파일이라도 내용이 완전히 같다면 같은 Blob 객체 ID를 사용할 수 있다.

### 2-2. Index에 `newFile → a123`이 등록된다

Index는 다음 커밋에 넣을 내용을 지정하는 목록이다. 일반 저장소에서 관련 정보는 보통 `.git/index`에 저장된다.

```text
Index (Staging Area)
┌──────────────────────────────┐
│ 파일 경로     Blob 객체 ID   │
│ newFile      a123           │
└──────────────────────────────┘
                        │
                        ▼
                 Blob (a123)
                 ┌───────────┐
                 │ created   │
                 └───────────┘
```

정확히는 Index 항목에는 파일 경로와 객체 ID뿐 아니라 파일 모드 및 상태 정보도 포함된다. 위 그림은 학습에 필요한 부분만 표시했다.

### 2-3. 그러면 `add`가 끝난 상태는?

```text
작업 폴더                  Index                     객체 저장소

newFile                    newFile → a123            Blob a123
┌───────────┐                      │                 ┌───────────┐
│ created   │                      └────────────────>│ created   │
└───────────┘                                        └───────────┘

아직 새 Commit 없음 / 아직 커밋용 Tree 생성 전
```

핵심은 다음 두 가지다.

- `git add`는 **파일을 바로 커밋하는 명령이 아니다.**
- Git은 파일의 **현재 내용**을 Blob으로 저장하고, 그 Blob을 **어떤 경로로 다음 커밋에 포함할지** Index에 기록한다.

예를 들어 `add`를 한 다음 `newFile`을 다시 수정하면 작업 폴더의 파일은 바뀌지만, **Index는 재차 `add`하기 전까지 앞서 등록한 내용을 가리킨다.**

## 3. `git commit -m "add file"`: 하나의 버전이 완성된다

```bash
git commit -m "add file"
```

이번에는 Index에 기록된 파일 구성을 바탕으로 **Tree 객체**를 만들고, 그 Tree를 가리키는 **Commit 객체**를 생성한다.

### 3-1. Tree: 어떤 이름의 파일과 폴더가 있는가?

```text
Tree (t456) ― 루트 폴더의 구조
┌──────────────────────────────┐
│ 이름       종류       객체 ID │
│ newFile    blob       a123   │
└──────────────────────────────┘
                         │
                         ▼
                      Blob a123
                      ┌─────────┐
                      │ created │
                      └─────────┘
```

이 Tree에서 `newFile`이라는 **이름**과 Blob `a123`이 연결된다. 따라서 `newFile`은 Blob에 저장된 이름이 아니라 **Tree가 부여한 경로상의 이름**이다.

하위 폴더가 있다면 Tree는 Blob 대신 다른 **하위 Tree**를 가리킬 수도 있다.

```text
루트 Tree
├── newFile       ──> Blob a123
└── docs/         ──> 하위 Tree
                       └── intro.md ──> 또 다른 Blob
```

### 3-2. Commit: 이 구조를 언제, 누구의 버전으로 기록했는가?

```text
브랜치 main
    │
    ▼
Commit (c789)
┌──────────────────────────────┐
│ tree: t456                   │
│ parent: 없음 (첫 커밋)       │
│ author / committer / 날짜    │
│ message: add file            │
└──────────────────────────────┘
             │
             ▼
Tree (t456)
┌──────────────────────────────┐
│ newFile ────────────> a123   │
└──────────────────────────────┘
                         │
                         ▼
                     Blob (a123)
                     ┌───────────┐
                     │ created   │
                     └───────────┘
```

이제 Git에는 하나의 **커밋(버전)**이 생겼다. `main` 브랜치는 이 Commit `c789`를 가리킨다. 일반적인 브랜치 체크아웃 상태에서 `HEAD`는 `main`을 가리킨다.

정리하면:

- **Blob a123:** 파일의 내용 `created\n`
- **Tree t456:** 루트 폴더에 `newFile`이 있고, 내용은 Blob `a123`
- **Commit c789:** Tree `t456`을 사용하는 버전의 메타데이터와 메시지
- **main:** 현재 최신 커밋 `c789`를 가리키는 브랜치

### `.git` 안에 진짜로 저장될까?

그렇다. 다만 `.git/objects/`에 `created`라는 평문 파일이 보이는 방식은 아니다. Git 객체는 **종류·크기 등과 내용을 포함해 해시로 식별**되며, 일반적인 느슨한 객체(loose object)는 압축되어 저장된다. 이후 객체들이 pack 파일로 묶일 수도 있다.

```text
.git/
├── objects/               ← Blob·Tree·Commit 같은 객체의 저장 장소
│   └── ...
├── index                  ← 현재 스테이징 정보
├── HEAD                   ← 보통 현재 브랜치를 가리킴
└── refs/heads/main        ← main이 가리키는 Commit ID (일반적인 형태)
```

실제 참조는 `packed-refs` 등으로 관리될 수도 있다. 따라서 `.git`에서 특정 파일이 항상 이 위치에 낱개로 존재한다고 기대할 필요는 없다.

## 4. `git commit --amend`: 마지막 커밋 메시지를 바꾸면?

이제 파일 **내용은 전혀 수정하지 않고** 커밋 메시지만 바꿔보자.

```bash
git commit --amend -m "change commit command"
```

처음 배우는 사람은 이 명령을 보고 **기존 Commit `c789`의 메시지만 편집한다**고 생각하기 쉽다. 하지만 Git은 다르게 동작한다.

### 실행 전

```text
main ──> Commit c789
          ├── message: add file
          └── tree: t456
                       │
                       ▼
                   Tree t456
                   └── newFile → Blob a123 → created
```

### 실행 후

```text
main ──> Commit c790              (새 Commit 객체)
          ├── message: change commit command
          └── tree: t456           (기존 Tree 재사용)
                       │
                       ▼
                   Tree t456       (동일)
                   └── newFile → Blob a123 → created (동일)

기존 Commit c789는 이 과정에서 제자리 수정되지 않는다.
```

| 항목 | `--amend` 실행 전 | 실행 후 |
|---|---|---|
| Commit 객체 ID | `c789` | `c790` (**변경**) |
| Commit 메시지 | `add file` | `change commit command` (**변경**) |
| Tree 객체 ID | `t456` | `t456` (동일) |
| Blob 객체 ID | `a123` | `a123` (동일) |
| 파일 내용 | `created` | `created` (동일) |
| main이 가리키는 Commit | `c789` | `c790` (**이동**) |

**왜 새 Commit일까?** Git의 객체는 내용에 기반한 ID로 식별되므로, 커밋 메시지가 달라지면 커밋 객체의 내용도 달라지고 객체 ID도 달라진다. 기존 객체를 고치기보다 **새 커밋을 만들어 브랜치가 가리키는 대상을 바꾸는 것**이다.

이 예제는 **첫 커밋을 amend한 상황**이다. 기존 커밋을 완전히 없애는 뜻은 아니다. 이전 Commit `c789`는 즉시 삭제되지 않고 객체 저장소에 남아 있을 수 있지만, 더는 `main`에서 연결되지 않으므로 나중에 Git의 정리 대상이 될 수 있다.

> `--amend`는 메시지뿐 아니라 **스테이징된 내용까지 포함해** 최근 커밋을 새로 만들 수 있다. 따라서 이미 다른 사람에게 Push하여 공유한 커밋을 팀 합의 없이 amend하면 안 된다.

## 5. 버전이 두 개가 되면? (비교 그림)

`--amend`와 **새 커밋 추가**는 다른 작업이다. 이 차이까지 이해하면 버전 관리의 의미가 더 분명해진다.

예를 들어 파일 내용을 나중에 이렇게 바꿨다고 해보자.

**newFile (두 번째 버전)**

```text
created
updated
```

이를 새로 `add`하고 **일반 `commit`** 하면 기존 Commit을 교체하지 않고 새로운 Commit이 이전 Commit을 **부모(parent)**로 가리킨다.

```text
main
 │
 ▼
Commit c900 (두 번째 버전)
├── parent: c790 ─────────────────────────┐
└── tree: t900                             │
           │                              │
           ▼                              ▼
       Tree t900                      Commit c790 (첫 번째 버전)
       └── newFile → Blob b900         └── tree: t456
                     │                           │
                     ▼                           ▼
                ┌──────────┐               Tree t456
                │ created  │               └── newFile → Blob a123
                │ updated  │                             │
                └──────────┘                             ▼
                                                     ┌─────────┐
                                                     │ created │
                                                     └─────────┘
```

이것이 **버전 관리**의 본질이다. 최신 버전과 이전 버전이 각자의 Commit → Tree → Blob 연결을 통해 어떤 파일 내용이었는지 추적할 수 있다.

Git이 항상 변경된 줄만 저장하는 것은 아니다. 개념적으로는 각 커밋이 프로젝트의 **스냅샷**을 참조한다. 내용이 같은 객체를 재사용하고, 저장 효율을 위해 내부적으로 압축·패킹 등도 사용할 수 있다.

## 6. 딱 네 문장으로 정리

1. **파일 작성:** 작업 폴더에 `newFile`이라는 파일과 `created`라는 내용이 생긴다.
2. **`git add`:** 파일 내용의 **Blob**을 기록하고, **Index**에 `newFile → Blob ID`를 등록한다.
3. **`git commit`:** Index를 바탕으로 **Tree**와 **Commit**을 만들고, 브랜치가 새 Commit을 가리키도록 한다.
4. **`git commit --amend`:** 기존 Commit을 직접 수정하지 않고 **새 Commit을 만들어 교체**하며, 파일 내용이 같으면 Tree와 Blob은 재사용할 수 있다.

### 스스로 설명할 수 있다면 이해한 것이다

- Blob에는 왜 `newFile`이라는 파일명이 없을까?
- `add`를 했지만 `commit`하지 않았다면 새 버전이 완성된 것일까?
- 파일 내용은 같은데 `--amend` 후 커밋 ID가 다른 이유는 무엇일까?
- 파일의 두 번째 버전을 기록할 때 왜 이전 Commit과 연결될까?

> **한 문장 핵심:** Git은 파일 내용을 Blob에, 파일 경로와 폴더 구조를 Tree에, 그 상태를 하나의 버전으로 식별하는 정보를 Commit에 기록하고 서로의 **해시 참조 관계**로 이력을 관리한다.
